# Reviewer navigation paths

For software engineering: start at README, run the portable suite, inspect one policy module and its corresponding malformed-input tests, then read architecture boundaries. Assess explicit state and input contracts rather than file count.

For aerospace systems: read safety limits, landing concept, coordinate-frame assumptions and target validation blockers. Ask what sensor evidence is required before a proposed velocity becomes an actuator command.

For robotics research: inspect toy-model assumptions, fault scenarios and replay formats. Ask which uncertainties remain unmodeled and what experiment would discriminate between competing designs.

For admissions or internship discussion: read the contribution record, demo script and future project shortlist. Use accurate attribution and describe learning, iteration and unresolved evidence. No ranking here guarantees selection.

For a potential educator: follow the offline quickstart first. Educational suitability, curriculum alignment, accessibility and willingness to pay are unverified. Do not ask learners to arm hardware to complete a software lesson.

Acceptance: each path ends with evidence and limitations, not only marketing. These are draft navigation routes; actual reviewer usability must be observed.
